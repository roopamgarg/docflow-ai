## Notes
- Created 2026-09-01 from plan breakdown (source: `~/.claude/plans/build-a-simple-polished-parallel-spark.md`).
- **Highest-risk detail on the board.** Before moving on, render the boxes over a page and eyeball alignment — a silent conversion bug here only becomes visible much later, as misplaced highlights in 013.
- Confidence is deliberately `1.0` for this source. Interpretation uncertainty is expressed as match strength in 006/007, not here.
- **Conversion verified, not eyeballed.** `pdfPointToPagePixel` applies the scale-1 `viewport.transform` (`[1, 0, 0, -1, 0, 792]` for US Letter) exactly as pdf.js's own `TextLayer` does, so PDF `y = 700` lands at pixel `y = 92`. A run at `transform [12, 0, 0, 12, 72, 700]`, `width 92.04`, `height 12` yields `{ x0: 72, y0: 80, x1: 164.04, y1: 92 }` — confirmed against the fixture through the real pdf.js API.
- **pdf.js build:** imports `pdfjs-dist/legacy/build/pdf.mjs`, not `pdfjs-dist`. The modern build throws on load under Node 24 (`hashOriginal.toHex is not a function`) and pdf.js itself warns to use the legacy build off-browser. Same version, so the vendored `pdf.worker.min.mjs` still matches; keeping one build means the extraction path is testable in vitest's node environment with no worker at all (pdf.js parses inline when `Worker` is absent).
- **Box geometry:** the em-box sits above the baseline (`height` up from it), so descenders can reach a few pixels below `y1`. Chosen over pdf.js's ascent-adjusted placement to keep the conversion free of font metrics. Boxes are clamped to the page rect.
- **Word splitting:** pdf.js returns runs (usually whole lines), so runs are split on whitespace and the advance width is apportioned by character offset — exact for single-word runs, approximate within a run. Re-measuring glyph advances would mean re-implementing the font engine.
- **Char count** is non-whitespace characters per page: a scanned page's text layer is often whitespace-only, which must read as `0`.
- Fixture `__fixtures__/sample-invoice.pdf` is generated by `__fixtures__/make-sample-pdf.mjs` (uncompressed, explicit `Tm` matrices, built-in Helvetica). 3 pages of 612x792; page 3 has no text at all, standing in for a scanned page. Observed: `charCount` 49 / 16 / 0 and 7 / 3 / 0 words.
- Not registered in `providers/registry.ts` — that is ticket 008's job, along with the scanned-PDF fallback decision. Nothing imports this module yet, so it has not been exercised through a Turbopack browser bundle.
- **Unit tests added in `pdf-text.spec.ts`.** All of the implementer's worked numbers above were asserted exactly (not just toBeCloseTo-approved to some other value) and all passed against the real code and the real fixture: the `(72,700)`/`(72,0)` flip through `[1,0,0,-1,0,792]`, the `{x0:72,y0:80,x1:164.04,y1:92}` box for `transform:[12,0,0,12,72,700]`/`width:92.04`/`height:12`, the `Invoice`/`INV-1024` word split of `"Invoice INV-1024"`, `countTextLayerCharacters(["a b","  \n ","cd"]) === 4`, and the fixture's per-page `charCount` (49/16/0), per-page word counts (7/3/0) and `totalCharCount === 65`. Also covered: an explicit mirror-bug guard (`y !== 700`), the `x0<=x1`/`y0<=y1` invariant under two synthetic non-upright viewport transforms, the width:0/height:0 fallback to `hypot(transform)`, clamping into `0..viewport.width/height` on both edges, whitespace-only/empty `str` producing no words, that the fixture-loading tests confirmed real-PDF parsing works in vitest's Node environment with no worker, that `extractPdfText` does not mutate/detach the caller's `Uint8Array` (pdf.js gets a copy), and that garbage bytes reject with `ExtractionError` code `unreadable`. No production bugs found — every asserted number matched the implementation on the first run.
